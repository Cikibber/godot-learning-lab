# Classroom walkthroughs

## Teacher

1. **Sign in** with the invited account. Create a class (name, term, timezone — default Asia/Jakarta).
2. **Class overview → Enrollment:** create a class code (valid days, max uses). It is shown once; share it in person. Approve or reject each pending request. Rotate the code if it leaks.
3. **School computer sessions:** add each supervised Godot session (e.g. "Tuesday 13:00–14:30, Lab 2"). Students pick these in the project survey.
4. **Assignments:** add the readiness survey and Modules 1–8 as needed; set order and due date (class timezone); tick *Publish*. Close an assignment to stop new work. Republish or reorder freely — there is no rigid prerequisite chain.
5. **Reviews:** filter by module/status; open a submission to see recomputed checks (*verified* = from saved config, *reported* = from play), the code-question result, reflection, and transfer answer. Accept or request revision with evidence-based feedback. Passing checks is practice evidence, not a grade.
6. **Overview → Needs attention:** students with revisions, overdue work, or missing surveys.
7. **Surveys:** completion counts, per-question counts/percentages with skipped counts, and individual responses. Free text and private questions (R11, P9, P10, P14) are never aggregated. Responses are identified — not anonymous.
8. **Teams:** create teams, add 3–4 approved students (the database rejects a fifth member or a second active team even if two teachers click at once). Record a size exception reason only when needed. The private panel shows each student's format, roles, preferences, open-to-assignment answer, and sessions — advisory only.
9. **Projects & rubric:** review the submitted proposal version (approve or request changes). Review milestones; record an **individual editor-task observation** each time (e.g. "instanced the Coin scene and connected the signal"). Enter team scores (60) and each student's individual scores (40) with notes.
10. **Exports:** class overview → CSV buttons. Store files per school policy.
11. **Term end:** archive the class (no new work; nothing deleted). Retention is handled by the operator.

Use the **12-week plan & rubric** page (header link; printable) to share the rubric before proposals and plan editor access: supervised machine-hours = machines × reserved hours; if team + individual demand exceeds it, extend the calendar or simplify scope.

## Student

1. Read the privacy page. Sign in with the school account from your invitation.
2. Enter the class code on your home page. Wait for your teacher's approval.
3. Do the readiness survey (optional questions can be skipped; "not sure" is fine).
4. **Continue learning** opens the next assigned module. Read the short explanation and worked example.
5. In the activity: press *Start* (or click the play area) and use arrows/WASD or the on-screen pad; *Escape* leaves keyboard mode. Change the parameters, then *Run checks*. Prefer text? Use **Text/step mode** — it counts the same.
6. Answer the code question, the reflection, and the Godot transfer question. Work saves automatically ("Saved." appears only after the server confirms). *Submit to teacher* when ready; submitted work can't be changed — use *Start revision* after feedback.
7. Try the **"Try it in Godot"** card on a school computer: real GDScript for Godot 4.6.
8. Do the project survey. After your teacher forms teams, open **Team & project**: write the proposal together (one teammate's stale tab cannot overwrite another's save), submit, revise if changes are requested, then record the three milestones with school-storage links. Write your own private contribution statement for each milestone.
9. See your team's score and your own individual score when your teacher enters them.

## Shared-computer reminders

Always *Sign out* on shared machines (it also clears unsent local drafts). The lab never uploads or hosts Godot projects; keep source and exports in the school's approved storage and paste only the link.
